# 本地 Ollama Agentic Framework 后续开发路线

## 1. 当前项目状态

目前已经完成模型访问层、单工具调用链、第一版 `AgentLoop`、独立工具执行层和 JSON Schema 参数验证。当前架构大致为：

```text
Application
    │
    ▼
AgentLoop ──→ ToolExecutor ──→ ToolRegistry ──→ Tool
    │
    ▼
LLM Interface
    │
    ▼
OllamaClient
    │
    ▼
Ollama /api/chat
```

核心领域对象已经开始从 Ollama API 中解耦：

```text
Message
ToolCall
ModelResponse

Tool
ToolRegistry
```

目前已经明确以下设计原则：

```text
Agent Core
不依赖 Ollama wire format

Tool
不依赖 Ollama

ToolRegistry
不生成 Ollama schema

OllamaClient
负责：
    Message → Ollama JSON
    Tool → Ollama Tool Schema
    Ollama Response → ModelResponse
```

这一边界非常重要。未来即使替换为 vLLM、llama.cpp 或其他模型服务，Agent Runtime 理论上无需改变。

当前已经完成以下完整调用链：

```text
User
 ↓
LLM
 ↓
ToolCall
 ↓
ToolRegistry
 ↓
Tool.execute()
 ↓
Tool Result
 ↓
LLM
 ↓
Final Answer
```

Ollama 当前正式支持 single tool calling、parallel tool calling 和 multi-turn agent loop，因此我们后续的 Runtime 可以直接建立在这些底层能力之上。citeturn735399view0turn735399view3

第一版 `AgentLoop` 还负责：

```text
保留 assistant.tool_calls
追加 role="tool" 的执行结果
检测普通最终回答
把未知工具和执行异常变成模型可见的 observation
通过 max_steps 终止重复调用
```

具体实现和实验见：[Phase 2 AgentLoop 实现记录](./Phase%202%20-%20AgentLoop%20实现记录.md)。

Phase 3 已经把工具执行职责从 `AgentLoop` 移到 `ToolExecutor`，并用 `ToolResult` 统一表达成功和失败。具体实现和实验见：[Phase 3 Runtime 实现记录](./Phase%203%20-%20Runtime%20实现记录.md)。

参考资料：  
Ollama Tool Calling：https://docs.ollama.com/capabilities/tool-calling  
Ollama Chat API：https://docs.ollama.com/api/chat

# 2. 项目的长期目标

最终目标不是做一个“能调用工具的聊天机器人”，而是实现一个小型但完整的 Agent Runtime：

```text
                   ┌─────────────┐
                   │    User     │
                   └──────┬──────┘
                          ▼
                   ┌─────────────┐
                   │    Agent    │
                   └──────┬──────┘
                          ▼
                  ┌───────────────┐
                  │   AgentLoop   │
                  └───────┬───────┘
                          │
          ┌───────────────┼────────────────┐
          ▼               ▼                ▼
        State            LLM          ToolRegistry
                          │                │
                          ▼                ▼
                     OllamaClient       Runtime
                                           │
                                  ┌────────┼────────┐
                                  ▼        ▼        ▼
                                Tool    Policy    Sandbox
```

从工程角度定义：

\[
Agent = Model + State + Tools + ControlLoop + Policy
\]

模型只是其中一个组件，而不是整个 Agent。

我们的核心目标是让模型负责：

```text
判断下一步做什么
```

而 Python Runtime 负责：

```text
是否允许
参数是否合法
怎样执行
是否失败
是否重试
何时停止
如何记录
```

这是后续所有设计的主轴。

参考资料：  
Ollama multi-turn tool calling 示例：https://docs.ollama.com/capabilities/tool-calling

# 3. 开发路线

1. **Phase 1：完成 Tool Calling**

   目标是完整跑通：

   ```text
   User
    ↓
   LLM
    ↓
   ToolCall(name, arguments)
    ↓
   ToolRegistry.execute()
    ↓
   Tool Result
    ↓
   role="tool"
    ↓
   LLM
    ↓
   Final Answer
   ```

   第一阶段只使用简单的 `multiply(a, b)` 工具。

   验收条件：

   ```text
   输入：
   What is 23 multiplied by 47?

   模型：
   ToolCall(
       name="multiply",
       arguments={"a": 23, "b": 47}
   )

   Runtime：
   1081

   模型最终：
   ...1081...
   ```

   此阶段重点不是数学，而是理解：

   ```text
   assistant.tool_calls
   tool result
   conversation history
   provider adapter
   ```

   Ollama 当前明确要求把 assistant 的 tool call 保留在消息历史中，并在其后追加 `role="tool"` 的执行结果。citeturn735399view0

   参考资料：  
   https://docs.ollama.com/capabilities/tool-calling

2. **Phase 2：实现真正的 `AgentLoop`**

   当前 Tool Calling 流程还是硬编码的：

   ```text
   LLM
   Tool
   LLM
   End
   ```

   下一步把它抽象为：

   ```python
   while step < max_steps:
       response = llm.chat(...)

       if not response.tool_calls:
           return response

       execute_tools(...)
       append_results(...)
   ```

   最终形成：

   ```text
   Observation
       ↓
   Decision
       ↓
   Action
       ↓
   Observation
       ↓
   Decision
       ↓
      ...
   ```

   这是整个项目真正的核心。

   第一版 `AgentLoop` 必须有：

   ```text
   max_steps
   final response detection
   tool execution
   message history update
   unknown tool handling
   tool exception handling
   ```

   最重要的安全机制之一是：

   ```text
   max_steps
   ```

   因为小模型非常容易出现：

   ```text
   call tool
      ↓
   call same tool
      ↓
   call same tool
      ↓
   ...
   ```

   Runtime 必须能够终止循环。

   参考资料：  
   Ollama Agent Loop：https://docs.ollama.com/capabilities/tool-calling

3. **Phase 3：建立 Runtime 层**（✅ 已完成第一版）

   此时不要继续让 `AgentLoop` 直接调用：

   ```python
   registry.execute(...)
   ```

   而是引入：

   ```text
   ToolExecutor
   ```

   架构变成：

   ```text
   AgentLoop
       ↓
   ToolExecutor
       ↓
   ToolRegistry
       ↓
   Tool
   ```

   原因是以后执行工具之前需要增加：

   ```text
   参数验证
   权限检查
   timeout
   retry
   logging
   resource limits
   ```

   最终希望得到：

   ```text
   ToolCall
      ↓
   Validation
      ↓
   Permission
      ↓
   Execution
      ↓
   ToolResult
   ```

   此阶段应定义统一：

   ```text
   ToolResult
   ```

   例如：

   ```python
   ToolResult(
       success=True,
       value=1081,
       error=None,
   )
   ```

   而不是让异常直接穿透整个 Agent。

   参考资料：  
   Python exceptions：https://docs.python.org/3/tutorial/errors.html  
   Ollama tool execution model：https://docs.ollama.com/capabilities/tool-calling

4. **Phase 4：参数 Schema 与验证**（✅ 已完成第一版）

   `ToolExecutor` 现在会在 handler 执行前，使用 `Tool.parameters` 验证模型产生的参数：

   ```text
   ToolCall
       ↓
   ToolRegistry.get(...)
       ↓
   ToolArgumentsValidator
       ↓
   Tool.execute(...)
       ↓
   ToolResult
   ```

   第一版选择 `jsonschema` 的 Draft 2020-12 validator，已经验证：

   ```text
   number / string / integer / boolean
   required / additionalProperties
   enum
   minimum / maximum
   array
   nested object
   ```

   发给模型的 schema 和 Runtime 使用的 schema 现在拥有同一个 source of truth：

   ```text
   Tool.parameters
       ├──→ OllamaClient → 模型工具描述
       └──→ ToolArgumentsValidator → Runtime 参数验证
   ```

   Pydantic 仍可在未来用于从 Python model 生成 schema，但当前没有引入第二份模型定义。具体实现和实验见：[Phase 4 Schema Validation 实现记录](./Phase%204%20-%20Schema%20Validation%20实现记录.md)。

   参考资料：  
   JSON Schema：https://json-schema.org/  
   Ollama Structured Outputs：https://docs.ollama.com/capabilities/structured-outputs citeturn735399view1

5. **Phase 5：扩展多工具能力**

   calculator 不应该只有 `multiply`。

   可以逐步加入：

   ```text
   add
   subtract
   multiply
   divide
   ```

   然后测试：

   ```text
   Calculate (12 + 7) × 5
   ```

   理想轨迹：

   ```text
   LLM
    ↓
   add(12, 7)
    ↓
   19
    ↓
   LLM
    ↓
   multiply(19, 5)
    ↓
   95
    ↓
   LLM
    ↓
   Final Answer
   ```

   这会首次真正测试：

   ```text
   multi-step reasoning
   tool selection
   intermediate state
   AgentLoop
   ```

   之后再测试一次产生多个独立 tool calls 的场景。

   Ollama 当前也支持 parallel tool calling，因此后期 Runtime 可以区分：

   ```text
   sequential tool calls

   与

   parallel tool calls
   ```

   但不要在第一版 AgentLoop 就实现并发。citeturn735399view0

   参考资料：  
   Ollama Parallel Tool Calling：https://docs.ollama.com/capabilities/tool-calling

6. **Phase 6：Agent State 与 Context Builder**

   到这一步，不能继续把：

   ```python
   messages: list[Message]
   ```

   当作整个 Agent 状态。

   应开始定义：

   ```text
   AgentState
   ```

   大致包含：

   ```text
   messages
   current_task
   step
   max_steps
   tool_history
   metadata
   ```

   同时引入：

   ```text
   ContextBuilder
   ```

   负责决定：

   ```text
   哪些信息发给模型
   哪些历史丢弃
   哪些历史摘要
   哪些工具提供给模型
   ```

   这里会第一次真正触及：

   ```text
   context engineering
   ```

   而不仅仅是 prompt engineering。

   Ollama `/api/chat` 的调用端负责提交消息历史，因此上下文管理最终属于我们的 Runtime，而不是 Ollama 自动替我们完成。citeturn735399view3

   参考资料：  
   Ollama Chat API：https://docs.ollama.com/api/chat

7. **Phase 7：短期记忆**

   第一版 memory 不需要向量数据库。

   先实现：

   ```text
   ConversationMemory
   ```

   负责：

   ```text
   append
   retrieve
   truncate
   summarize
   ```

   研究重点应该是：

   ```text
   context window
   token budget
   sliding window
   summary memory
   ```

   可以逐渐实现：

   ```text
   最近 N 条完整消息
          +
   更早内容的摘要
   ```

   这一阶段的目标不是“无限记忆”，而是：

   > 控制上下文长度，同时尽量保留完成当前任务所需要的信息。

   参考资料：  
   Ollama Chat API：https://docs.ollama.com/api/chat

8. **Phase 8：长期记忆 / Retrieval**

   短期 memory 稳定后，再引入：

   ```text
   LongTermMemory
   ```

   可以从最简单的 SQLite 开始：

   ```text
   id
   text
   created_at
   metadata
   ```

   然后加入：

   ```text
   embedding
   semantic retrieval
   ```

   架构：

   ```text
   User Query
      ↓
   Embedding
      ↓
   Vector Search
      ↓
   Relevant Memories
      ↓
   ContextBuilder
      ↓
   LLM
   ```

   Ollama 当前提供独立的 embedding 能力，因此仍然可以保持整个系统完全本地。citeturn735399view2

   这一阶段重点学习：

   ```text
   chunking
   embeddings
   cosine similarity
   top-k retrieval
   metadata filtering
   memory write policy
   ```

   参考资料：  
   Ollama Embeddings：https://docs.ollama.com/capabilities/embeddings  
   SQLite：https://www.sqlite.org/docs.html

9. **Phase 9：Planner / Executor**

   到这个阶段再加入：

   ```text
   Planner
   ```

   而不是一开始就做规划。

   架构可以是：

   ```text
   User Task
      ↓
   Planner
      ↓
   Plan
      ↓
   Executor
      ↓
   Tool Loop
      ↓
   Result
   ```

   例如：

   ```text
   用户：
   读取 sales.csv，计算平均销售额，
   然后把结果保存到 report.txt

   Planner：

   1. read_file
   2. calculate
   3. write_file
   ```

   这里非常适合利用 structured output，让 Planner 返回固定结构，而不是靠自由文本解析。

   Ollama 当前可以使用 JSON Schema 约束结构化输出。citeturn735399view1

   参考资料：  
   Ollama Structured Outputs：https://docs.ollama.com/capabilities/structured-outputs

10. **Phase 10：Reflection / Error Recovery**

   Planner 稳定后再研究：

   ```text
   Critic
   Reflection
   Retry
   ```

   不应该设计成模型无限“反思”。

   应由 Runtime 控制：

   ```text
   attempt 1
      ↓
   error
      ↓
   classify error
      ↓
   retryable?
      ↓
   yes → retry
   no  → stop
   ```

   Reflection 主要用于：

   ```text
   工具参数错误
   子任务失败
   结果不满足预期格式
   ```

   而 timeout、权限拒绝、资源不足这类问题应由程序直接处理，不应让 LLM 自己猜。

   参考资料：  
   Ollama Structured Outputs：https://docs.ollama.com/capabilities/structured-outputs  
   Python exceptions：https://docs.python.org/3/tutorial/errors.html

11. **Phase 11：权限、安全与 Sandbox**

   在加入下面这些工具之前：

   ```text
   filesystem
   shell
   Python execution
   HTTP
   browser
   ```

   必须先实现：

   ```text
   PermissionPolicy
   ```

   最终执行链：

   ```text
   LLM
    ↓
   ToolCall
    ↓
   Schema Validation
    ↓
   PermissionPolicy
    ↓
   Sandbox / Executor
    ↓
   Tool Result
   ```

   filesystem 应至少支持：

   ```text
   workspace root
   allowed paths
   read/write distinction
   path traversal prevention
   ```

   shell 应至少考虑：

   ```text
   timeout
   working directory
   allowed commands
   environment isolation
   output limit
   ```

   核心原则：

   > LLM 可以提出 Action，但不能决定它是否有权限执行。

   参考资料：  
   Python pathlib：https://docs.python.org/3/library/pathlib.html  
   Python subprocess：https://docs.python.org/3/library/subprocess.html

12. **Phase 12：Observability**

   Agent 一复杂，就不能只靠：

   ```python
   print(...)
   ```

   应开始建立事件系统：

   ```text
   AgentStarted
   ModelCalled
   ModelReturned
   ToolRequested
   ToolStarted
   ToolFinished
   ToolFailed
   AgentFinished
   ```

   之后可以记录：

   ```text
   step count
   tool calls
   latency
   prompt tokens
   completion tokens
   errors
   final status
   ```

   Ollama `/api/chat` 当前会返回 `prompt_eval_count`、`eval_count` 以及若干 timing metadata，因此可以直接纳入 trace。citeturn735399view3

   第一版保存成：

   ```text
   JSONL
   ```

   就足够。

   不需要马上使用大型 observability 平台。

   参考资料：  
   Ollama Chat API：https://docs.ollama.com/api/chat  
   Python logging：https://docs.python.org/3/library/logging.html

13. **Phase 13：Evaluation**

   这是非常重要但经常被忽视的一层。

   建立：

   ```text
   evals/
       calculator.json
       tool_selection.json
       error_recovery.json
   ```

   测试案例例如：

   ```text
   23 × 47
       → 必须选择 multiply
       → arguments 正确
       → result = 1081

   hello
       → 不应该调用 calculator

   multiply 3 and ...
       → 应正确处理缺失信息
   ```

   可以逐渐统计：

   ```text
   task success rate
   correct tool rate
   argument accuracy
   average steps
   unnecessary tool calls
   token usage
   latency
   ```

   特别是本项目使用小模型时，Evaluation 比继续堆 Prompt 更重要。

   每修改：

   ```text
   model
   prompt
   tool description
   AgentLoop
   ```

   都应该重新跑 eval。

   参考资料：  
   Ollama API metrics：https://docs.ollama.com/api/chat

14. **Phase 14：并发与 Parallel Tool Calling**

   AgentLoop 稳定后，再支持：

   ```text
   response.tool_calls = [
       A,
       B,
       C
   ]
   ```

   如果这些工具之间无依赖，可以并行执行：

   ```text
             ┌→ Tool A ─┐
   LLM ──────┼→ Tool B ─┼→ observations
             └→ Tool C ─┘
   ```

   Python 层可以研究：

   ```text
   asyncio
   TaskGroup
   async HTTP client
   ```

   但要注意：

   ```text
   parallel
   ≠
   sequential planning
   ```

   `A → B → C` 有数据依赖时不能盲目并发。

   Ollama 当前提供 parallel tool calling，可以作为这一阶段的 provider 能力基础。citeturn735399view0

   参考资料：  
   Ollama Parallel Tool Calling：https://docs.ollama.com/capabilities/tool-calling  
   Python asyncio：https://docs.python.org/3/library/asyncio.html

15. **Phase 15：Multi-Agent**

   Multi-Agent 最后再做。

   当单 Agent Runtime 已经具备：

   ```text
   Tool
   State
   Memory
   Planner
   Runtime
   Policy
   Trace
   Eval
   ```

   后，再研究：

   ```text
   Supervisor
       ↓
   ┌───┼────┐
   ▼   ▼    ▼
   A   B    C
   ```

   此时 Worker Agent 本质上只是：

   ```text
   一个拥有特定 prompt
   +
   特定 tools
   +
   特定 permissions
   的 Agent Runtime
   ```

   不要把 Multi-Agent 当成一种完全不同的系统。

   它更多是：

   ```text
   Agent Runtime
       +
   orchestration
   ```

   参考资料：  
   Ollama Multi-turn Tool Calling：https://docs.ollama.com/capabilities/tool-calling

# 5. 推荐的实现优先级

接下来真正值得按顺序完成的是：

```text
当前
 │
 ▼
Tool Calling
 │
 ▼
AgentLoop              ← 最重要
 │
 ▼
ToolResult / Executor
 │
 ▼
Validation
 │
 ▼
Multiple Tools
 │
 ▼
AgentState
 │
 ▼
Context Management
 │
 ▼
Logging + Trace
 │
 ▼
Evaluation
 │
 ├──────────→ Safety / Sandbox
 │
 ├──────────→ Long-term Memory
 │
 └──────────→ Planning
```

我建议把：

```text
AgentLoop
Runtime
Evaluation
```

视为项目主干。

而：

```text
Memory
Planner
Reflection
Multi-Agent
```

视为建立在主干上的能力插件。

这样即使未来某一种 Agent 设计路线被证明效果不好，也不需要重写整个 Runtime。

参考资料：  
Ollama Tool Calling：https://docs.ollama.com/capabilities/tool-calling  
Ollama Chat API：https://docs.ollama.com/api/chat

# 6. 暂时不要急着做的东西

目前不建议马上加入：

```text
LangChain
LangGraph
AutoGen
CrewAI

Vector DB
复杂 RAG

Browser Agent

Shell unrestricted execution

Multi-Agent

复杂 UI
```

不是因为这些没有价值，而是它们会遮住我们当前真正需要学习的核心问题：

```text
LLM 为什么决定调用工具？

工具调用怎样进入历史？

Agent 为什么会无限循环？

什么应该属于模型决策？

什么应该属于 Runtime？

状态怎样管理？
```

# 7. 建议维护一份 Architecture Decision Record

随着项目深入，建议建立：

```text
docs/
└── decisions.md
```

记录类似：

```text
ADR-001
使用 JSON Schema 作为 Tool input schema

原因：
通用、成熟、可验证，且 Ollama 能直接映射。

ADR-002
Tool Core 不依赖 Ollama wire format

原因：
避免 provider coupling。

ADR-003
使用 127.0.0.1 而不是 localhost

原因：
当前 Windows 环境中 localhost 路径存在异常，
127.0.0.1 与 Ollama 默认 IPv4 loopback 工作稳定。

ADR-004
LLM output 一律视为 untrusted input

因此：
ToolCall 必须经过 validation 与 permission check。
```

这会比单纯保存代码更有学习价值，因为你以后可以看到整个框架“为什么变成现在这样”。

Architecture Decision Records：https://adr.github.io/

# 8. 每个阶段都问三个问题

后续增加任何组件时，都建议固定问：

```text
① 这个概念属于哪一层？

② 它依赖了谁？
   这个依赖方向是否合理？

③ 怎样证明它真的工作？
```

例如 Memory：

```text
属于：
Agent State / Context

不应该：
直接依赖 OllamaClient

验证：
跨多个 turn 是否正确保留必要信息
```

例如 filesystem：

```text
属于：
Tool + Runtime

不应该：
让 LLM 直接操作 pathlib

验证：
正常路径、越界路径、只读路径、异常路径
```

这三个问题会让这个项目从“Agent Demo”逐渐变成真正的软件系统。

参考资料：  
Python Software Design / ABC：https://docs.python.org/3/library/abc.html

# 9. 最值得深入研究的五个主题

完成最小 Runtime 后，最值得深入的方向不是立刻增加更多工具，而是：

```text
Agent Control Loop
    模型和程序分别控制什么？

Context Engineering
    模型每一步到底应该看到什么？

Tool Interface Design
    工具粒度怎样影响小模型决策能力？

Evaluation
    怎样证明 prompt / model / architecture 改动真的有效？

Runtime Safety
    如何把“不可信模型输出”安全地转换成真实世界 Action？
```

这五个主题基本贯穿今天主流 Agent 系统设计。

Memory、RAG、Planner、Multi-Agent 最终都可以看作是在回答其中某一个问题。
