```text
Application

    ▼

```

核心领域对象已经开始从 Ollama API 中解耦：

```text
Message
ToolCall
ModelResponse
    content / thinking / tool_calls

Tool
ToolRegistry
```

目前已经明确以下设计原则：

```text
Agent Core
不依赖 Ollama wire format

Tool
不依赖 Ollama

ToolRegistry
不生成 Ollama schema

OllamaClient
负责：
    Message → Ollama JSON
    Tool → Ollama Tool Schema
    Ollama Response → ModelResponse
```

这一边界非常重要。未来即使替换为 vLLM、llama.cpp 或其他模型服务，Agent Runtime 理论上无需改变。

当前已经完成以下完整调用链：

```text

ToolCall
 ↓
ToolRegistry
 ↓
Tool.execute()
 ↓
Tool Result
 ↓
LLM
 ↓
Final Answer
```

Ollama 当前正式支持 single tool calling、parallel tool calling 和 multi-turn agent loop，因此我们后续的 Runtime 可以直接建立在这些底层能力之上。

第一版 `AgentLoop` 还负责：

```text

追加 role="tool" 的执行结果
检测普通最终回答
```

# 2. 项目的长期目标

最终目标不是做一个“能调用工具的聊天机器人”，而是实现一个小型但完整的 Agent Runtime：

```text
                   ┌─────────────┐
                   │    User     │
                   └──────┬──────┘
                          ▼
                   ┌─────────────┐
                   │    Agent    │
                   └──────┬──────┘
                          ▼
                  ┌───────────────┐
                  │   AgentLoop   │
                  └───────┬───────┘
                          │
          ┌───────────────┼────────────────┐
          ▼               ▼                ▼
        State            LLM          ToolRegistry
                          │                │
                          ▼                ▼
                     OllamaClient       Runtime
                                           │
                                  ┌────────┼────────┐
                                  ▼        ▼        ▼
                                Tool    Policy    Sandbox
```

从工程角度定义：

\[
Agent = Model + State + Tools + ControlLoop + Policy
\]

模型只是其中一个组件，而不是整个 Agent。

我们的核心目标是让模型负责：

```text
判断下一步做什么
```

而 Python Runtime 负责：

```text
是否允许
参数是否合法
怎样执行
是否失败
是否重试
何时停止
如何记录
```

这是后续所有设计的主轴。

参考资料：  
Ollama multi-turn tool calling 示例：https://docs.ollama.com/capabilities/tool-calling

# 3. 开发路线

1. **Phase 1：完成 Tool Calling**（✅ 已完成）

   目标是完整跑通：

   ```text
   User
    ↓
   LLM
    ↓
   ToolCall(name, arguments)
    ↓
   ToolRegistry.execute()
    ↓
   Tool Result
    ↓
   role="tool"
    ↓
   LLM
    ↓
   Final Answer
   ```

   第一阶段只使用简单的 `multiply(a, b)` 工具。

   验收条件：

   ```text
   输入：
   What is 23 multiplied by 47?

   模型：
   ToolCall(
       name="multiply",
       arguments={"a": 23, "b": 47}
   )

   Runtime：
   1081

   模型最终：
   ...1081...
   ```

   此阶段重点不是数学，而是理解：

   ```text
   assistant.tool_calls
   tool result
   conversation history
   provider adapter
   ```

   Ollama 当前明确要求把 assistant 的 tool call 保留在消息历史中，并在其后追加 `role="tool"` 的执行结果。

   参考资料：  
   https://docs.ollama.com/capabilities/tool-calling

2. **Phase 2：实现真正的 `AgentLoop`**（✅ 已完成第一版）

   最初的 Tool Calling 流程是硬编码的：

   ```text
   LLM
   Tool
   LLM
   End
   ```

   目前已经把它抽象为：

   ```python
   while step < max_steps:
       response = llm.chat(...)

       if not response.tool_calls:
           return response

       execute_tools(...)
       append_results(...)
   ```

   最终形成：

   ```text
   Observation
       ↓
   Decision
       ↓
   Action
       ↓
   Observation
       ↓
   Decision
       ↓
      ...
   ```

   这是整个项目真正的核心。

   第一版 `AgentLoop` 必须有：

   ```text
   max_steps
   final response detection
   tool execution
   message history update
   unknown tool handling
   tool exception handling
   ```

   最重要的安全机制之一是：

   ```text
   max_steps
   ```

   因为小模型非常容易出现：

   ```text
   call tool
      ↓
   call same tool
      ↓
   call same tool
      ↓
   ...
   ```

   Runtime 必须能够终止循环。

   参考资料：  
   Ollama Agent Loop：https://docs.ollama.com/capabilities/tool-calling

3. **Phase 3：建立 Runtime 层**（✅ 已完成第一版）

   此时不要继续让 `AgentLoop` 直接调用：

   ```python
   registry.execute(...)
   ```

   而是引入：

   ```text
   ToolExecutor
   ```

   架构变成：

   ```text
   AgentLoop
       ↓
   ToolExecutor
       ↓
   ToolRegistry
       ↓
   Tool
   ```

   原因是以后执行工具之前需要增加：

   ```text
   参数验证
   权限检查
   timeout
   retry
   logging
   resource limits
   ```

   最终希望得到：

   ```text
   ToolCall
      ↓
   Validation
      ↓
   Permission
      ↓
   Execution
      ↓
   ToolResult
   ```

   此阶段应定义统一：

   ```text
   ToolResult
   ```

   例如：

   ```python
   ToolResult(
       success=True,
       value=1081,
       error=None,
   )
   ```

   而不是让异常直接穿透整个 Agent。

   Phase 7D 进一步补充了一个必须早于完整 PermissionPolicy 固化的安全不变量：
   `available_tools()` 不只是模型提示信息，也是执行 capability。即使工具仍在
   Registry、模型从历史恢复了正确调用，当前不可用的工具也会在参数验证和 handler
   前返回 `tool_not_available`。详见
   [Phase 7D Tool Capability Enforcement 实现记录](./Phase%207D%20-%20Tool%20Capability%20Enforcement%20实现记录.md)。

   参考资料：  
   Python exceptions：https://docs.python.org/3/tutorial/errors.html  
   Ollama tool execution model：https://docs.ollama.com/capabilities/tool-calling

4. **Phase 4：参数 Schema 与验证**（✅ 已完成第一版）

   `ToolExecutor` 现在会在 handler 执行前，使用 `Tool.parameters` 验证模型产生的参数：

   ```text
   ToolCall
       ↓
   ToolRegistry.get(...)
       ↓
   ToolArgumentsValidator
       ↓
   Tool.execute(...)
       ↓
   ToolResult
   ```

   第一版选择 `jsonschema` 的 Draft 2020-12 validator，已经验证：

   ```text
   number / string / integer / boolean
   required / additionalProperties
   enum
   minimum / maximum
   array
   nested object
   ```

   发给模型的 schema 和 Runtime 使用的 schema 现在拥有同一个 source of truth：

   ```text
   Tool.parameters
       ├──→ OllamaClient → 模型工具描述
       └──→ ToolArgumentsValidator → Runtime 参数验证
   ```

   Pydantic 仍可在未来用于从 Python model 生成 schema，但当前没有引入第二份模型定义。具体实现和实验见：[Phase 4 Schema Validation 实现记录](./Phase%204%20-%20Schema%20Validation%20实现记录.md)。

   参考资料：  
   JSON Schema：https://json-schema.org/  
   Ollama Structured Outputs：https://docs.ollama.com/capabilities/structured-outputs

5.5. **Phase 5.5：人类可读日志与 Thinking 捕获**（✅ 已完成第一版）

   为了让本地模型实验可以被观察和复现，本阶段提前加入了基础 observability 层：

   ```text
   AgentLoop
       ↓ emits
   Structured Events
       ↓ formats
   HumanReadableLogger
   ```

   已完成：

   ```text
   模型调用和响应日志
   tool call、tool result 和异常日志
   Agent 开始、结束和 max_steps 日志
   NullLogger 默认静默行为
   Ollama message.thinking → ModelResponse.thinking
   thinking 与最终 content 分栏显示
   空响应诊断，且空 assistant 消息不进入 conversation history
   ```

   对 `qwen3.5:9b` 的真实实验确认：部分表面上的空响应并非完全没有输出，而是模型只返回了 `thinking`，`content` 为空并以 `done_reason=stop` 结束。这说明：

   ```text
   thinking 是诊断信息
   thinking 不等于最终回答
   thinking 不能参与完成判定、权限决策或参数验证
   ```

   当前 Logger 会记录 thinking，但 Agent 的正式消息历史还不会回放它。完整的 reasoning continuity 留给 Phase 6。

   具体实现和实验见：[Phase 5.5 Human Readable Logging 实现记录](./Phase%205.5%20-%20Human%20Readable%20Logging%20实现记录.md)。

6. **Phase 6：Agent State、Reasoning Continuity 与 Context Builder**（⬅️ 当前阶段）

   本阶段解决两个相关但不同的问题：

   ```text
   运行轨迹是否完整保存
   下一轮模型是否需要看到上一轮决策依据
   ```

   `messages` 只表示发给模型的正式对话，不能继续兼任整个 Agent 状态。与此同时，仅保存 tool call 和 tool result 会丢失“为什么做这个实验”。复杂任务中，下一轮模型可能重新推理、重复调用工具，或误读刚得到的 observation。

   本阶段分为三个小阶段，逐步引入这些能力，并保持默认行为兼容。

   ### Phase 6A：AgentState 与 AgentStep（✅ 已完成）

   先定义完整的运行状态和逐步轨迹：

   ```text
   AgentState
       trajectory
       step
       max_steps
       metadata

   InputMessage
       message

   AgentStep
       step
       model_response
           content
           thinking
           tool_calls
           token metadata
       tool_executions

   ToolExecution
       call
       result
   ```

   `AgentStep` 保存每次模型响应以及随后产生的工具结果。这样，即使 thinking 不进入消息上下文，Trajectory 仍然完整保留它，Logger、评估器和调试工具也能读取同一份事实来源。

   正式 conversation messages 不再存储于 `AgentState`，而是由
   `ConversationProjector` 从 trajectory 确定性投影。它们继续只表达：

   ```text
   assistant content
   assistant tool calls
   tool results
   ```

   验收条件：

   ```text
   AgentLoop 不再用分散的局部变量表达运行状态
   每一轮 ModelResponse 都进入 AgentStep，包括 content 为空的响应
   每个工具结果都能关联到产生它的 step
   现有默认日志和工具调用行为保持不变
   max_steps、未知工具和异常路径仍能正确结束
   ```

   当前实现已让 `AgentState` 成为运行状态的唯一事实来源，并通过
   `InputMessage`、`AgentStep` 和 `ToolExecution` 保存输入、模型响应及工具
   调用与结果的显式关联。空响应和 thinking-only 响应保留在 trajectory
   中，但 `ConversationProjector` 不会将它们投影为正式消息。
   `AgentRunResult` 在暴露 `state`、完整 `trajectory` 和 `agent_steps` 的
   同时，保留旧的 messages、steps 和 tool_results 访问方式。具体实现和
   实验见：
   [Phase 6A Agent State 与 Trajectory 实现记录](./Phase%206A%20-%20Agent%20State%20与%20Trajectory%20实现记录.md)。

   ### Phase 6B：ReasoningBlock 与 Provider Capability（✅ 已完成）

   在完整轨迹之上，为 provider reasoning 加入来源和 replay capability：

   ```text
   ReasoningBlock
       provider
       model
       raw thinking / provider state
       replayable

   ```

   `ReasoningBlock` 用于同一 provider、同一 model 的短期 reasoning continuation。只有 provider adapter 明确声明支持回放时，Runtime 才能使用它。Ollama 能返回 `message.thinking`，并不自动证明它能正确消费历史 thinking；必须通过独立实验验证请求格式和实际行为。

   必须保持以下边界：

   ```text
   reasoning 不混入 assistant content
   thinking 不被当作最终回答
   reasoning 不参与权限判断和工具参数验证
   raw thinking 不无限期保留在模型上下文中
   provider 不支持 replay 时安全降级为正式 messages
   ```

   验收条件：

   ```text
   adapter 能显式报告 reasoning replay capability
   不支持 replay 的模型保持当前行为
   ```

   当前实现已加入 provider capability 声明、带 provider/model provenance 的
   `ReasoningBlock`。Ollama 官方 tool-calling 文档明确展示了把 thinking
   放回后续 assistant message，因而 adapter 声明传输层支持 replay；默认
   ConversationProjector 仍不会回放。
   DecisionMemo 暂缓实现，等 Reasoning Replay 策略成熟后再根据实际缺口设计。
   具体实现和调查证据见：
   [Phase 6B Reasoning Continuity 实现记录](./Phase%206B%20-%20Reasoning%20Continuity%20实现记录.md)。

   ### Phase 6C：ContextBuilder 与回放策略（✅ 已完成）

   引入 `ContextBuilder`，统一决定本轮实际发送给模型的 messages：

   ```text
   如何从 Trajectory 投影正式消息
   是否回放最近的 reasoning block
   ```

   历史截断、摘要、memory 和工具选择不属于 Phase 6C 第一版，继续留给后续
   阶段。`ConversationProjector` 保持无策略，只负责 canonical projection；
   `ContextBuilder` 在其结果之上应用调用级策略。

   第一版策略：

   ```text
   reasoning_replay = off | latest_pending

   默认：off
   ```

   `latest_pending` 只允许回放最近一个仍与当前 observation 相关、尚未完成的
   reasoning block。它检查 adapter capability、provider/model provenance、
   replayable 标记和 tool observation 完整性。inert empty step 可以跳过；新的
   非空决策 step 会形成陈旧 reasoning 屏障。更早的 raw thinking 不进入模型
   上下文。

   对 `qwen3.5:9b` 做 A/B 实验，比较：

   ```text
   最终答案成功率
   空 content 响应数
   重复工具调用数
   平均 step 数
   prompt / completion token
   latency
   ```

   已在 WSL Mirror 模式、Linux `.venv` 中重新完成本地 `qwen3.5:9b` 的 3 × 2
   次小样本实验。两组成功率均为 100%，平均 step 均为 3，空响应和重复调用
   均为 0；off 平均延迟 3.58 秒，latest_pending 平均延迟 3.33 秒。
   `latest_pending` 共实际回放 6 次。两组 prompt token 都是 2071，这是未解释
   的观察，不能过度推断；简单任务样本也不足以证明 replay 有收益。因此默认
   继续保持 `off`。完整测试记录见 [Ollama WSL Mirror 集成测试记录](./2026-09-22%20Ollama%20WSL%20Mirror%20集成测试记录.md)。

   具体实现、选择算法和实验数据见：
   [Phase 6C ContextBuilder 实现记录](./Phase%206C%20-%20Context%20Builder%20实现记录.md)。

   Ollama `/api/chat` 的调用端负责提交消息历史，因此上下文管理最终属于我们的 Runtime，而不是 Ollama 自动替我们完成。

   参考资料：  
   Ollama Chat API：https://docs.ollama.com/api/chat

7. **Phase 7：短期记忆（✅ 7A—7C 已完成）**

   Phase 7A 已实现 ConversationMemory 和 AgentSession：会话持有最近 N 个
   完整已完成轮次，每次用历史创建新 State，只提交当前轮增量，失败不提交，
   深拷贝隔离可变消息。窗口以完整轮次淘汰，不拆开工具调用与 observation。
   默认 N=5，system prompt 独立保留，raw thinking 不跨轮保存。
   详见 [Phase 7A 实现记录](./Phase%207A%20-%20Conversation%20Memory%20实现记录.md)。
   Phase 7B 已用真实 `qwen3.5:9b` 验证跨轮引用、事实更新、完整轮次淘汰与长
   工具结果。3 次小样本中四类场景均成功；长工具结果让最终查询达到 2182
   prompt tokens，而普通 recall 为 92，证明轮数窗口不能替代上下文预算。
   Phase 7C 已实现完整轮次粒度、可观察的 history character budget：存储仍由
   `max_turns` 控制，检索时选择预算内最新连续 suffix，并暴露 selected、dropped
   和 character 指标。精确 token budget 与 summarize 仍为后续目标。详见
   [Phase 7C 实现记录](./Phase%207C%20-%20History%20Character%20Budget%20实现记录.md)。

   第一版 memory 不需要向量数据库。

   先实现：

   ```text
   ConversationMemory
   ```

   负责：

   ```text
   append
   retrieve
   truncate
   summarize
   ```

   研究重点应该是：

   ```text
   context window
   token budget
   sliding window
   summary memory
   ```

   可以逐渐实现：

   ```text
   最近 N 条完整消息
          +
   更早内容的摘要
   ```

   这一阶段的目标不是“无限记忆”，而是：

   > 控制上下文长度，同时尽量保留完成当前任务所需要的信息。

   参考资料：  
   Ollama Chat API：https://docs.ollama.com/api/chat

8. **Phase 8：长期记忆 / Retrieval**

    Phase 8A 已完成：`LongTermMemory` 接口、SQLite namespace 隔离文本/metadata
    持久化、显式写入与按需字面子串检索；`AgentSession` 可选注入带来源的非可信
    检索数据，默认无自动写入或读取。实现及离线实验见
    [Phase 8A SQLite 长期记忆实现记录](./Phase%208A%20-%20SQLite%20长期记忆实现记录.md)。
     Phase 8B 已为显式检索增加可选 JSON payload 字符预算、整条记录选择和
     可观察的候选/选中/排除指标；见
     [Phase 8B 长期记忆检索预算实现记录](./Phase%208B%20-%20长期记忆检索预算实现记录.md)。
     Phase 8C 已加入可替换 embedding 接口及 SQLite 余弦 top-k 语义检索，
     已用 `qwen3-embedding:0.6b` 做 4 题小样本检索和一次端到端回答验证；详见
     [Phase 8C SQLite 语义检索实现记录](./Phase%208C%20-%20SQLite%20语义检索实现记录.md)。
     自动写入与统一 trace 仍待后续阶段。

   Phase 7D 完成后，已经具备进入 Phase 8A 的最小安全前提：长期记忆中出现旧工具
   名称或参数不会自动恢复执行 capability。第一小步应限定为 Memory interface、
   SQLite 文本/metadata 持久化和显式读写策略；检索内容必须作为不可信 data，而非
   instruction。embedding、自动写入和跨用户共享继续后置。

   短期 memory 稳定后，再引入：

   ```text
   LongTermMemory
   ```

   可以从最简单的 SQLite 开始：

   ```text
   id
   text
   created_at
   metadata
   ```

   然后加入：

   ```text
   embedding
   semantic retrieval
   ```

   架构：

   ```text
   User Query
      ↓
   Embedding
      ↓
   Vector Search
      ↓
   Relevant Memories
      ↓
   ContextBuilder
      ↓
   LLM
   ```

   Ollama 当前提供独立的 embedding 能力，因此仍然可以保持整个系统完全本地。

   这一阶段重点学习：

   ```text
   chunking
   embeddings
   cosine similarity
   top-k retrieval
   metadata filtering
   memory write policy
   ```

   参考资料：  
   Ollama Embeddings：https://docs.ollama.com/capabilities/embeddings  
   SQLite：https://www.sqlite.org/docs.html

9. **Phase 9：Planner / Executor**

   到这个阶段再加入：

   ```text
   Planner
   ```

   而不是一开始就做规划。

   架构可以是：

   ```text
   User Task
      ↓
   Planner
      ↓
   Plan
      ↓
   Executor
      ↓
   Tool Loop
      ↓
   Result
   ```

   例如：

   ```text
   用户：
   读取 sales.csv，计算平均销售额，
   然后把结果保存到 report.txt

   Planner：

   1. read_file
   2. calculate
   3. write_file
   ```

   这里非常适合利用 structured output，让 Planner 返回固定结构，而不是靠自由文本解析。

   Ollama 当前可以使用 JSON Schema 约束结构化输出。

   参考资料：  
   Ollama Structured Outputs：https://docs.ollama.com/capabilities/structured-outputs

10. **Phase 10：Reflection / Error Recovery**

   Planner 稳定后再研究：

   ```text
   Critic
   Reflection
   Retry
   ```

   不应该设计成模型无限“反思”。

   应由 Runtime 控制：

   ```text
   attempt 1
      ↓
   error
      ↓
   classify error
      ↓
   retryable?
      ↓
   yes → retry
   no  → stop
   ```

   Reflection 主要用于：

   ```text
   工具参数错误
   子任务失败
   结果不满足预期格式
   ```

   而 timeout、权限拒绝、资源不足这类问题应由程序直接处理，不应让 LLM 自己猜。

   参考资料：  
   Ollama Structured Outputs：https://docs.ollama.com/capabilities/structured-outputs  
   Python exceptions：https://docs.python.org/3/tutorial/errors.html

11. **Phase 11：权限、安全与 Sandbox**

   在加入下面这些工具之前：

   ```text
   filesystem
   shell
   Python execution
   HTTP
   browser
   ```

   必须先实现：

   ```text
   PermissionPolicy
   ```

   最终执行链：

   ```text
   LLM
    ↓
   ToolCall
    ↓
   Schema Validation
    ↓
   PermissionPolicy
    ↓
   Sandbox / Executor
    ↓
   Tool Result
   ```

   filesystem 应至少支持：

   ```text
   workspace root
   allowed paths
   read/write distinction
   path traversal prevention
   ```

   shell 应至少考虑：

   ```text
   timeout
   working directory
   allowed commands
   environment isolation
   output limit
   ```

   核心原则：

   > LLM 可以提出 Action，但不能决定它是否有权限执行。

   参考资料：  
   Python pathlib：https://docs.python.org/3/library/pathlib.html  
   Python subprocess：https://docs.python.org/3/library/subprocess.html

12. **Phase 12：Observability**（✅ 完成）

    Phase 5.5 已提前完成基础事件类型、Logger 接口和人类可读终端输出。Phase 12A
    补充了 run/step ID、UTC 时间戳、单调时钟耗时；Phase 12B 完成了逐事件 JSONL v1
    持久化与整轮调用/错误/token/耗时指标。默认 trace 不存原文，显式开启才记录
    内容。详情见 [Phase 12A 实现记录](./Phase%2012A%20-%20Run%20Step%20标识与计时实现记录.md)
    与 [Phase 12B 实现记录](./Phase%2012B%20-%20JSONL%20Trace%20与运行指标实现记录.md)。

   Agent 一复杂，就不能只靠：

   ```python
   print(...)
   ```

   应开始建立事件系统：

   ```text
   AgentStarted
   ModelCalled
   ModelReturned
   ToolRequested
   ToolStarted
   ToolFinished
   ToolFailed
   AgentFinished
   ```

   之后可以记录：

   ```text
   step count
   tool calls
   latency
   prompt tokens
   completion tokens
   errors
   final status
   ```

   Ollama `/api/chat` 当前会返回 `prompt_eval_count`、`eval_count` 以及若干 timing metadata，因此可以直接纳入 trace。

   第一版保存成：

   ```text
   JSONL
   ```

   就足够。

   不需要马上使用大型 observability 平台。

   参考资料：  
   Ollama Chat API：https://docs.ollama.com/api/chat  
   Python logging：https://docs.python.org/3/library/logging.html

13. **Phase 13：Evaluation**

   这是非常重要但经常被忽视的一层。

   建立：

   ```text
   evals/
       calculator.json
       tool_selection.json
       error_recovery.json
   ```

   测试案例例如：

   ```text
   23 × 47
       → 必须选择 multiply
       → arguments 正确
       → result = 1081

   hello
       → 不应该调用 calculator

   multiply 3 and ...
       → 应正确处理缺失信息
   ```

   可以逐渐统计：

   ```text
   task success rate
   correct tool rate
   argument accuracy
   average steps
   unnecessary tool calls
   token usage
   latency
   ```

   特别是本项目使用小模型时，Evaluation 比继续堆 Prompt 更重要。

   每修改：

   ```text
   model
   prompt
   tool description
   AgentLoop
   ```

   都应该重新跑 eval。

   参考资料：  
   Ollama API metrics：https://docs.ollama.com/api/chat

14. **Phase 14：并发与 Parallel Tool Calling**

   AgentLoop 稳定后，再支持：

   ```text
   response.tool_calls = [
       A,
       B,
       C
   ]
   ```

   如果这些工具之间无依赖，可以并行执行：

   ```text
             ┌→ Tool A ─┐
   LLM ──────┼→ Tool B ─┼→ observations
             └→ Tool C ─┘
   ```

   Python 层可以研究：

   ```text
   asyncio
   TaskGroup
   async HTTP client
   ```

   但要注意：

   ```text
   parallel
   ≠
   sequential planning
   ```

   `A → B → C` 有数据依赖时不能盲目并发。

   Ollama 当前提供 parallel tool calling，可以作为这一阶段的 provider 能力基础。

   参考资料：  
   Ollama Parallel Tool Calling：https://docs.ollama.com/capabilities/tool-calling  
   Python asyncio：https://docs.python.org/3/library/asyncio.html

15. **Phase 15：Multi-Agent**

   Multi-Agent 最后再做。

   当单 Agent Runtime 已经具备：

   ```text
   Tool
   State
   Memory
   Planner
   Runtime
   Policy
   Trace
   Eval
   ```

   后，再研究：

   ```text
   Supervisor
       ↓
   ┌───┼────┐
   ▼   ▼    ▼
   A   B    C
   ```

   此时 Worker Agent 本质上只是：

   ```text
   一个拥有特定 prompt
   +
   特定 tools
   +
   特定 permissions
   的 Agent Runtime
   ```

   不要把 Multi-Agent 当成一种完全不同的系统。

   它更多是：

   ```text
   Agent Runtime
       +
   orchestration
   ```

   参考资料：  
   Ollama Multi-turn Tool Calling：https://docs.ollama.com/capabilities/tool-calling

# 8. 每个阶段都问三个问题

后续增加任何组件时，都建议固定问：

```text
① 这个概念属于哪一层？

② 它依赖了谁？
   这个依赖方向是否合理？

③ 怎样证明它真的工作？
```

例如 Memory：

```text
属于：
Agent State / Context

不应该：
直接依赖 OllamaClient

验证：
跨多个 turn 是否正确保留必要信息
```

例如 filesystem：

```text
属于：
Tool + Runtime

不应该：
让 LLM 直接操作 pathlib

验证：
正常路径、越界路径、只读路径、异常路径
```

这三个问题会让这个项目从“Agent Demo”逐渐变成真正的软件系统。

参考资料：  
Python Software Design / ABC：https://docs.python.org/3/library/abc.html

# 9. 最值得深入研究的五个主题

完成最小 Runtime 后，最值得深入的方向不是立刻增加更多工具，而是：

```text
Agent Control Loop
    模型和程序分别控制什么？

Context Engineering
    模型每一步到底应该看到什么？

Tool Interface Design
    工具粒度怎样影响小模型决策能力？

Evaluation
    怎样证明 prompt / model / architecture 改动真的有效？

Runtime Safety
    如何把“不可信模型输出”安全地转换成真实世界 Action？
```

这五个主题基本贯穿今天主流 Agent 系统设计。

Memory、RAG、Planner、Multi-Agent 最终都可以看作是在回答其中某一个问题。
