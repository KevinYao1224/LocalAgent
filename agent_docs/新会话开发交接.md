## 2. 当前架构

```text
Application
    │
    ▼
AgentLoop ──→ AgentState / Trajectory
    ├──→ ConversationProjector ──→ canonical messages
    ├──→ ToolExecutor ──→ ToolRegistry ──→ Tool
    ├──→ Observability Events ──→ HumanReadableLogger / NullLogger
    └──→ LLM Interface ──→ OllamaClient ──→ Ollama /api/chat
```

当前状态边界：

```text
AgentState.trajectory
    输入消息、模型响应以及工具调用与结果的完整运行事实

AgentState.steps
    从 trajectory 派生的 AgentStep 视图

ConversationProjector
    从 trajectory 确定性生成正式 conversation messages
```

`AgentRunResult.state` 是运行状态的唯一事实来源。旧接口仍兼容：

```python
result.messages
result.steps
result.tool_results
```

完整轨迹通过 `result.trajectory` 访问；仅模型步骤通过
`result.agent_steps` 或 `result.state.steps` 访问。

## 3. Phase 6A 的关键结论

必须继续保持：

```text
1. 每个 ModelResponse 都进入 AgentStep。
2. thinking-only 和全空响应不被投影为正式 messages。
3. thinking 保存在 trajectory，但不自动回放。
4. thinking 不是最终答案，也不参与权限和参数验证。
5. ToolExecution 显式关联 ToolCall、ToolResult 和产生它的 AgentStep。
6. provider 调用失败不会虚构 ModelResponse 或 AgentStep。
7. AgentLoop.last_state 可用于检查异常发生前的状态。
8. AgentState 不构造 messages；ConversationProjector 负责确定性投影。
```

本地 `qwen3.5:9b` 过去出现过：

```text
Model thinking: The result ... is 95.
Model content: <empty>
Tool calls: 0
done_reason=stop
```

这只证明 Ollama 会返回 `message.thinking`，不证明它能消费或正确延续历史
reasoning。不能把 thinking 复制到 assistant content，也不能仅凭
`done_reason=stop` 把 thinking 当最终回答。

## 4. Phase 6B 的目标

下一阶段先定义用途不同的两类信息：

```text
ReasoningBlock
    provider
    model
    raw thinking / provider state
    replayable

DecisionMemo
    goal
    hypothesis
    action_reason
    expected_observation
    next_if_success
    next_if_failure
```

`ReasoningBlock` 只服务同 provider、同 model 的短期 continuation，并且只有
adapter 明确报告支持时才允许回放。

`DecisionMemo` 是 provider-neutral 的简短决策摘要，用于旧步骤、模型切换、
不支持 raw reasoning replay 的 provider，以及未来的上下文压缩。

Phase 6B 的验收条件：

```text
原始 thinking 与 DecisionMemo 在类型上可区分
ReasoningBlock 能关联到对应 AgentStep
adapter 明确暴露 reasoning replay capability
不支持 replay 的 provider 保持现有行为
默认配置不回放 reasoning
DecisionMemo 能关联到对应 AgentStep 和 ToolCall
```

## 5. Phase 6B 开始前要先调查的问题

不要直接假设 Ollama 的请求格式。先通过文档和一个最小真实实验确认：

```text
Ollama /api/chat 是否接受历史 thinking 或 provider state
请求字段是什么
是否只对部分模型有效
模型或 provider 切换时如何降级
回放后是否减少空响应和重复工具调用
```

如果 provider 没有明确支持，应将 capability 标记为不支持，并保持正式
messages + DecisionMemo 的安全路径。

## 6. 本阶段不要提前实现

Phase 6B 不应同时完成：

```text
完整 ContextBuilder
历史截断或摘要策略
短期记忆
JSONL trace
权限系统
自动改变默认 reasoning replay 策略
```

先建立可区分、可关联的数据类型和 provider capability，再在 Phase 6C 设计
哪些信息实际进入上下文。
