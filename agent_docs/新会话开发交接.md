## 4. Qwen thinking 的关键发现

真实 `qwen3.5:9b` 实验确认，此前观察到的部分“空响应”其实包含 thinking：

```text
Model thinking:
  The result of (12 + 7) multiplied by 5 is 95.
Model content: <empty>
Tool calls: 0
completion=20
done_reason=stop
```

旧 adapter 只读取 `message.content`，因此 Runtime 看到了空响应。现在 `OllamaClient` 会把 `message.thinking` 写入 `ModelResponse.thinking`，Logger 也会单独显示它。

这个实验同时证明：

```text
thinking 是模型的中间状态和诊断数据
thinking 不等于面向用户的最终答案
done_reason=stop 也不能让 thinking 自动成为 final content
```

模型之后可能重复调用工具，并最终触发 `max_steps`。因此不能用“把 thinking 当回答”来修复空响应。

## 5. 必须保持的设计约束

Phase 6 开发应保持以下不变量：

```text
1. Agent Core 不依赖 Ollama wire format。
2. LLM 输出一律视为不可信输入。
3. thinking 不参与权限、参数验证或工具执行授权。
4. thinking 不参与最终回答判定。
5. reasoning 不混入 assistant content。
6. 空 content 且无 tool_calls 的 assistant 消息不进入 conversation history。
7. 所有 ModelResponse 都应进入 trajectory，包括 thinking-only 和空响应。
8. 原始 reasoning 不应无限期回放或占据上下文。
9. provider 不支持 reasoning replay 时必须能安全降级。
10. 默认配置应保持 Phase 5.5 的现有行为。
```

尤其要区分：

```text
Conversation messages
    发给模型的正式协议历史

Trajectory
    Runtime 保存的完整执行事实

Reasoning replay
    ContextBuilder 有条件选择的模型输入
```

保存 thinking 到 Trajectory，并不意味着必须把它重新发送给模型。

## 6. Phase 6 的精确拆分

### Phase 6A：AgentState 与 AgentStep

建议先定义：

```text
AgentState
    messages
    current_task
    step
    max_steps
    steps
    tool_results
    metadata

AgentStep
    step
    model_response
        content
        thinking
        tool_calls
        token metadata
    tool_results
```

迁移顺序：

```text
1. 新增状态和 step 类型。
2. 让 AgentLoop 用 AgentState 管理 history、step 和 tool_results。
3. 每次 LLM 返回后立即创建 AgentStep。
4. 工具执行完成后，把 ToolResult 关联到当前 AgentStep。
5. 让 AgentRunResult 暴露最终 state 或 steps。
6. 保持现有调用方和日志实验通过。
7. 增加一个 trajectory 实验，展示正常、thinking-only、工具失败和 max_steps 路径。
8. 编写 Phase 6A 实现记录。
```

Phase 6A 的验收条件：

```text
AgentLoop 不再用分散局部变量表示完整运行状态
每个 ModelResponse 都可在 AgentStep 中找到
每个 ToolResult 都关联到产生它的 step
messages 中仍只包含正式 content / tool_calls / tool results
空 assistant 响应不进入 messages，但保留在 steps
完成、异常和 max_steps 路径都有可检查的 trajectory
现有实验保持通过
```

### Phase 6B：ReasoningBlock 与 DecisionMemo

Phase 6A 稳定后再定义：

```text
ReasoningBlock
    provider
    model
    raw thinking / provider state
    replayable

DecisionMemo
    goal
    hypothesis
    action_reason
    expected_observation
    next_if_success
    next_if_failure
```

`ReasoningBlock` 只服务同 provider、同 model 的短期 continuation。adapter 必须显式报告是否支持 replay。不能因为 Ollama 会返回 `message.thinking`，就假定它接受或正确使用历史 thinking。

`DecisionMemo` 是 provider-neutral 的简短决策摘要，用于旧步骤、上下文压缩、模型切换和不支持 reasoning replay 的情况。

### Phase 6C：ContextBuilder

第一版策略接口：

```text
reasoning_replay = off | latest_pending
default = off
```

`latest_pending` 最多回放最近一个仍相关、尚未完成的 reasoning block。旧 reasoning 应移除或转成 DecisionMemo。

需要对 `qwen3.5:9b` 做 A/B 实验，比较：

```text
最终答案成功率
空 content 响应数
重复工具调用数
平均 step 数
prompt / completion token
latency
```
